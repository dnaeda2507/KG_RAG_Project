  1. PIPELINE ARCHITECTURE
══════════════════════════════════════════════════════════════════════════

  2. MODULE DESCRIPTIONS
══════════════════════════════════════════════════════════════════════════

──────────────────────────────────────────────────────────────────────────
  2.1  Module 1 — Spreading Activation (Neo4j)
──────────────────────────────────────────────────────────────────────────

  File: kg_infused_rag/phase4_pipeline/module1_spreading_activation.py

  The spreading activation algorithm traverses the Wikidata5M graph outward
  from question-related seed entities. It weights each activated node by
  its relationship distance from the seed.

  Parameters used:
    depth      = 2  (expands 2 hops from seed)
    max_nodes  = 100  (caps subgraph size per seed)
    decay      = 0.5  (activation weight halved per hop)

  A Cypher query retrieves all neighbours within the depth limit. Triples
  are returned as (subject, relation, object) tuples annotated with their
  activation weight.

  Key challenge: Seed entity resolution
    The question contains a Turkish film/person name. The pipeline
    attempts alias matching via wikidata5m_entity.txt. Turkish special
    characters (ş ğ ü ö ı ç) sometimes prevent exact matching.
    Example: "halit refiğ" fails alias lookup due to ğ → no seed entity
    found → spreading activation returns empty subgraph.

  Output: list of triples with score, e.g.:
    [("Q_film", "DIRECTOR", "Q_director", 1.0),
     ("Q_director", "PLACE_OF_BIRTH", "Q_city", 0.5)]


──────────────────────────────────────────────────────────────────────────
  2.2  Module 2 — Query Expansion + Knowledge Retrieval
──────────────────────────────────────────────────────────────────────────

  File: kg_infused_rag/phase4_pipeline/module2_query_expansion.py

  Part A — KG Triple Selection
    The LLM (llama-3.3-70b-versatile via Groq API) is given the
    spreading-activation subgraph and asked to select the triples most
    relevant to answering the question. Selected triples become the
    structured knowledge context.

  Part B — KG-Guided Wikipedia Retrieval
    Entities extracted from the selected triples are used as Wikipedia
    search terms. The wikipedia Python library is called with lang="en".

    LIMITATION: Turkish film and person names in English Wikipedia are
    usually very short articles or do not exist. The library returns 0
    passages for most Turkish entity searches.

    Confirmed: In all 50 evaluated questions, passages = [].
    This means all four methods (incl. Vanilla RAG) had no retrieved
    text context — they differed only in KG triple availability.

  Output: selected_triples (list), passages (list — always [] in current run)


──────────────────────────────────────────────────────────────────────────
  2.3  Module 3 — Answer Generation
──────────────────────────────────────────────────────────────────────────

  File: kg_infused_rag/phase4_pipeline/module3_answer_generation.py

  For KG-RAG, the prompt template is:

    "Use the following knowledge graph triples and passages to answer
     the question. Answer in one phrase.

     Question: {question}
     KG Triples: {formatted triples}
     Passages: {formatted passages}

     Answer:"

  The LLM (llama-3.3-70b-versatile) generates a short phrase.
  For No-Retrieval, the prompt excludes triples and passages.
  For Vanilla RAG, only passages are in the prompt.
  For Vanilla QE, an expanded version of the question feeds the same prompt.

  3. EVALUATION METRICS
══════════════════════════════════════════════════════════════════════════

  Evaluated on 45 questions (50 total minus 5 COMPARISON:: questions).

  ─── soft_accuracy (primary) ──────────────────────────────────────────
  Condition 1: (gold_lower in prediction_lower)
  Condition 2: (prediction_lower in gold_lower) AND len(prediction) > 3
  soft_acc = 1.0 if Cond1 OR Cond2, else 0.0

  Example:
    gold = "istanbul (turkey)"  |  pred = "Istanbul, Turkey"
    → "istanbul (turkey)" not in "istanbul, turkey" → Cond1 fails
    → "istanbul, turkey" not in "istanbul (turkey)" → Cond2 fails
    → soft_acc = 0.0   ← known false negative

    gold = "Buffalora"  |  pred = "was born in Buffalora, Italy"
    → "buffalora" in "was born in buffalora, italy" → Cond1 passes
    → soft_acc = 1.0  ← correct ✓

  ─── F1 Score ──────────────────────────────────────────────────────────
  Token-level overlap between gold answer tokens and prediction tokens.
  All 4 methods scored 0.0 — caused by Turkish character encoding;
  tokenisation splits on unexpected byte boundaries when special
  characters appear in the prediction.

  ─── Exact Match (EM) ──────────────────────────────────────────────────
  Binary: 1 if gold == prediction (after lower-casing and strip).
  All 4 methods scored 0.0 — gold answers include parenthetical forms
  like "istanbul (turkey)" which the LLM never reproduces exactly.

  6. FAILURE ANALYSIS
══════════════════════════════════════════════════════════════════════════

  Three distinct failure patterns were observed:

  ─── Pattern 1: Gold answer format mismatch ───────────────────────────
  Count: ~15 questions (TR_001–TR_008 + others)
  Cause: Gold = "istanbul (turkey)" (Wikidata5M alias with parentheses);
         LLM returns "Istanbul, Turkey" or "İstanbul".
  Soft_acc logic: "istanbul (turkey)" not in "istanbul, turkey" → 0.0
  Fix: Normalise gold answers during dataset construction; remove
       parenthetical country annotations when city alone is sufficient.

  ─── Pattern 2: LLM returns "Cannot be determined" ───────────────────
  Count: ~12 questions (TR_003, TR_006–TR_008, TR_015–TR_019, TR_027–028)
  Cause: Spreading activation cannot find the Turkish entity in Neo4j
         (alias matching failure due to special characters); triples = []
         LLM's conservative refusal when no context triples are available.
  Details:
    TR_006: "nedim koçak" — ğ/ç in alias causing lookup failure
    TR_007: "ferzan özpetek" — ö character not normalised in alias file
    TR_008: "yavuz turgul" — no alias match found
  Fix: Normalise Turkish characters to ASCII equivalents during alias
       lookup (ş→s, ğ→g, ü→u, ö→o, ı→i, ç→c).

  ─── Pattern 3: Wrong entity answered ────────────────────────────────
  Count: ~4 questions
  Cause: KG subgraph activates multiple candidate entities; LLM selects
         the wrong one as the most "relevant" triple.
  Example:
    TR_016: question about a film's director birthplace
            gold = "Angora"  (Ankara's Wikidata alias)
            KG-RAG = "Mersin"  (different director entity activated)
  Fix: Improve entity disambiguation in Module 1 by additional relevance
       scoring; use film–director relation chain filtering.

  ─── Why all baselines scored 0.0% ───────────────────────────────────
  • passages = [] for all questions — Wikipedia library returned no text
    for Turkish film/person queries in English Wikipedia
  • Therefore: Vanilla RAG and Vanilla QE had NO retrieved context
  • No-Retrieval: LLM has very little parametric knowledge of Turkish films
  • All 3 non-KG methods were effectively identical and scored 0.0%
  • KG-RAG advantage: structured triples from Neo4j supplied city names
    directly, allowing 4 correct answers despite 0 Wikipedia passages

  7. KEY TAKEAWAYS
══════════════════════════════════════════════════════════════════════════

  1. KG triples alone (without any Wikipedia retrieval) give 8.89% accuracy,
     demonstrating that the KG-infusion module adds concrete value even
     under adverse retrieval conditions.

  2. The dominant failure mode is NOT wrong LLM reasoning — it is upstream
     alias matching failure (Turkish characters) and gold-answer format
     mismatch. Both are engineering solvable.

  3. Using wikidata5m_text.txt as the retrieval corpus (instead of Wikipedia)
     would provide text that matches the KG's entity aliases exactly. This is
     the most impactful planned improvement.

  4. F1 and EM both report 0.0% due to Turkish encoding bugs unrelated to
     factual correctness. Soft_accuracy is the only valid metric here.

  5. 3-hop questions (0.0%) were harder: the LLM must chain three reasoning
     steps from limited triple context. Providing more explicit chain-of-
     thought prompting is a planned improvement.
